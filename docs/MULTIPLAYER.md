# Optional two-player cooperative games

A creator enables **Allow two players to play together online** on an arcade game, saves it, playtests its saved levels and publishes the reviewed edition. The game keeps its normal **Play solo** option. Word games remain single-player. Existing versions 1–3 are unchanged; opting in creates version 4, retaining the version 2 level plan and layout seeds.

On the published game's page, choose **Invite a friend** and copy the private invitation to the other player. The second player opens that link in another browser session or device. Alternatively, choose **Find a partner** to explicitly offer the free seat in the public **Looking for a partner** section. Private rooms remain the default and never appear there. The host starts the shared round once both players are connected. Both players see the same obstacles and collectibles, with two friendly characters/ships and separate controls, lives, collection goals and arcade point totals. Projectiles cannot damage a teammate. In timed campaigns, both players must reach their own collection goal; the round ends if time expires or both players lose their lives. Endless survival has no timer or collection win. The host controls start, pause, restart and level progression. The second player controls their own character.

Multiplayer supports the fixed collect, dodge/shooting and platformer engines. The public lobby offers a single open seat, without chat, spectators, player profiles, a skill-matching algorithm or competitive play. Browser-host simulation is an advisory play observation. Cooperative-enabled editions do not submit to the existing solo leaderboard or assignment points SDK; a future host integration must explicitly bind each player's observations to its own approved assessment workflow. NCAcademy's current pinned arcade importer continues to receive only supported versions 1–2.

## Looking for a partner

The Games homepage and workshop overview show **Looking for a partner**. Only hosts who choose **Find a partner** are listed. A listed room has its published game title and one open guest seat; **Join game** opens that game's page with a public room ID and asks the relay for the seat. The room ID is a navigation hint, not a private invitation or seat capability. A private invitation can still claim that same seat; whichever valid join succeeds first wins it atomically. If someone else fills the seat first, the later player receives an unavailable-room message and can choose another game.

The directory contains at most 20 rooms for this installation. It includes only current published multiplayer editions whose host is connected and whose guest seat is unclaimed. Filled, closed, expired, host-absent and changed-publication rooms are filtered out. Refreshing the directory does not renew room activity. The interface refreshes periodically while visible and offers a manual refresh. It is a current-availability view; another player can take a seat between listing and joining.

A public Join game click reserves the seat for 45 seconds while that player connects. If they leave before admission, the seat reappears and another player can claim it; the expired capability cannot admit its former holder. A successful admission seals the seat for that guest's reconnects and never turns a disconnected player into a replaceable public seat. Private invitation claims retain their existing one-use behavior.

Listing is anonymous and includes only `roomId`, `gameId`, `publishedRevision`, `specSha256`, the already-public game `title`, and the room's current lease `expiresAt`. It never exposes invite, host or guest tokens, names, email addresses, account IDs, private drafts or gameplay state. Someone using the site can occupy an explicitly public open seat. Keep an invitation private when you want to choose your teammate.

## Connection and lifecycle

The parent page connects to a managed WebSocket relay. The host browser advances one shared world; the guest sends only a six-button input mask. The host transmits bounded snapshots at ten per second. Every snapshot is validated against the fixed schema, edition and numerical/entity bounds. No generated code, remote assets, model calls or networking permissions enter the opaque sandbox. The iframe retains its own no-network content security policy, nonce and strict source-window checks. The existing version 1 host completion envelope is unchanged; cooperative play does not emit it.

The server binds a room to the current published game ID, edition and SHA-256 definition hash. Publication condition checks share atomic transactions with admission and relay leases; unpublishing or publishing another edition invalidates the room. Active rooms have no fixed 30-minute age limit. Admission and authenticated socket heartbeats renew a 30-minute idle lease; a new `lease` message updates the client's deadline. The server enforces logical expiry even while a DynamoDB TTL record still exists. Public directory reads and failed admission attempts do not renew that lease. Host absence still ends a room after the existing bounded reconnect grace; an active guest cannot keep an abandoned host's room alive.

The current client requests renewable leases with `leaseVersion: 1` in its first socket admission message. Older clients receive their original ready/peer/pong shapes and original seat deadline, without an unfamiliar lease event. After releasing this feature, open a fresh page and start a new room to use renewal; a previously opened legacy page is not silently converted into a different protocol.

An invitation or public lobby join admits exactly one guest atomically. Losing a connection pauses the game and clears held inputs. The same page can reconnect briefly using the same seat capability, preserving its current world, level, elapsed time, lives and points; the host explicitly resumes. There is no host migration. Leaving/closing the host room ends it for both players. Reloading a page loses its in-memory capability, so use a new room rather than treating reload as a saved session.

AWS API Gateway still limits each individual WebSocket connection to two hours and closes idle connections after ten minutes. These are [transport limits](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-execution-service-websocket-limits-table.html), separate from the renewable room lease. The existing heartbeat/reconnect flow can replace a socket in the same room without restarting its game. A long network outage, closed host tab or lost page capability can still end play; the application does not promise an uninterrupted permanent socket.

Room, host, invite and guest capabilities are separate random values. Only their SHA-256 hashes are stored. The invite uses a URL fragment, which is removed before joining; capabilities travel in POST bodies and the first WebSocket message, never query parameters, public catalog data or iframe/host events. Public lobby links use `/games/{gameId}?room={roomId}` with no capability. The page consumes that hint once; the server independently checks the room's public visibility, current publication, connected host and unclaimed seat. Treat an invitation as private: anyone holding an unused invitation can occupy its one guest seat. There are no names, emails, student IDs or Core access tokens in the room protocol.

Increasing sequence numbers and connection generations prevent replay and stale disconnects from controlling a replacement socket. Per-source admission limits, short connection leases, message-size/rate bounds, aggregate API throttles and logical expiration bound abuse. The initial socket stage admits 100 messages/second with a burst of 200 across the installation, so it is intended for a small number of concurrent rooms. A larger class rollout needs a reviewed aggregate limit and concurrency/load test. These controls are not a monetary spending cap. The host pauses the shared game when its tab becomes hidden; returning requires an explicit resume. Keep the host's game tab active: browser throttling, latency and device performance can affect a browser-host simulation. This is cooperative play, not an anti-cheat server or an authoritative grading service.

## Retention and authority

The additive relay has its own encrypted on-demand DynamoDB table for capability hashes, game binding, short connection leases, a bounded installation-scoped public waiting-room index and hashed admission counters. It stores no gameplay snapshots, chat, names or student records. The lobby uses exact-key reads and conditional transactions in that same table; it needs no table scan, new database or private-table grant. TTL removes expired records asynchronously. Lambda retains infrastructure diagnostics for seven days; socket payload tracing and access logs are disabled. Application code never prints request bodies or capabilities. Normal AWS platform telemetry may still include network metadata. TLS protects HTTPS/WSS transport and DynamoDB service encryption protects stored ephemeral records.

The relay adds `GET /multiplayer/lobby` and `POST /multiplayer/rooms/{roomId}/lobby-join` to its existing HTTP proxy. Room creation optionally accepts `visibility: "public"` or `"private"`; omitting it retains private invitations. A public join contains only the exact game ID, published revision and definition hash. Every successful join returns a new guest capability in its normal private response. The existing HTTP API already allows GET and routes through its fixed `$default` proxy; this extension does not require another gateway, route permission, identity grant or paid service.

The relay's dedicated role can read and condition-check the exact existing published-games table; it cannot write there. It can operate its own room table, send/delete connections on its own WebSocket API and write its own logs. It has no access to Core credentials, private drafts, student data, models or other application resources. The existing Core application stack and shared permission boundary remain unchanged. The extension is explicitly application-owned infrastructure and is released separately from Core's current fixed frontend/API recipe; later Core recipe adoption must preserve the existing room stack or perform a reviewed migration.

## Package and deploy

`infra/aws/multiplayer.template.json` creates the additional HTTP room API, WebSocket API, relay Lambda, retained TTL table, role and short-retention log group. It uses the same deterministic backend source archive as Game Studio. It reuses the verified application's private artifact bucket without changing its policy, DNS, domains or Core grants. API Gateway, Lambda, DynamoDB and build/storage traffic have normal usage charges; there is no always-running game server or TURN subscription.

Planning makes no cloud requests:

```sh
python3 scripts/deploy-multiplayer.py \
  --output /PRIVATE/RECEIPTS \
  --core-stack nce-YOUR-EXISTING-APPLICATION-STACK \
  --application-id YOUR-APPLICATION-UUID \
  --stack game-studio-YOUR-APPLICATION-multiplayer \
  --profile YOUR-PROFILE --expected-account YOUR-12-DIGIT-ACCOUNT
```

After reviewing the source and plan, repeat with `--execute --authorize-aws-charges` using a clean committed checkout. Execution verifies the account, exact Core application tags/identity, current origin, existing published-games table and bucket ownership. The change-set guard refuses resource removal/replacement and an existing extension cannot be reassigned to another tenant. The relay code hash and health endpoint must match before a receipt is written.

Copy the receipt's **publicConfig** into `public/multiplayer-config.json`, commit that public endpoint and release the frontend/API through the normal Core flow. The file contains only `{ "version": 1, "apiUrl": "https://..." }`; no keys, room capabilities or private settings belong there. Empty configuration leaves solo play available and explains that the relay is unavailable. For another environment, deploy a separate verified extension and use its matching configuration. Subsequent backend changes require both the extension script and the normal Core application release; deploying only the main API does not update the relay Lambda.

Rollback the frontend to a reviewed previous commit to remove the option. End/expire active rooms before changing the protocol. Keep the retained table and all existing Core application resources. The script refuses destructive changes; deleting infrastructure is a separately reviewed operation.

## Verification

Run `npm run typecheck`, `npm test`, `npm run test:api`, `python3 -m unittest discover -s scripts/tests`, `python3 scripts/validate-deployment.py`, `python3 scripts/package-api.py` and `npm run build:preview`. Engine tests check one world tick, independent inputs/collisions/goals/points, friendly-fire exclusion and strict sandbox state. Room tests cover capability storage, atomic single-guest admission, wrong seats, stale generations/sequences, expiry, publication changes, origin/rate/size bounds and private-state exclusion. Deployment tests verify the publication-only grant, callback scope, tenant immutability and retention. These local checks use synthetic data and call no model providers.

Run `npm run test:multiplayer-preview` for an isolated real-WebSocket network check; it starts and cleans up its own local servers and also runs in CI. Its version 6 endless fixture exercises private-room exclusion, opt-in token-free listing, competing public/invitation joins, full/absent/closed filtering and shared game state after heartbeat renewal past the original 30-minute deadline. A loopback-only synthetic clock advances the test without a real half-hour wait; no production route or clock is changed. For interactive inspection, run `npm run dev:multiplayer` and open `http://127.0.0.1:8096/__multiplayer-fixture` in two pages, then choose **Find a partner** in one and join from the other's Games homepage. This uses the production Python room logic with transient synthetic storage over actual localhost HTTP/WebSockets.

A preview is not AWS acceptance. After a real deployment, independently verify Lambda archive bytes, frontend source-build bytes, the exact configured HTTPS/WSS endpoints, API route permissions, private table scope, TTL, public health and protected authoring boundaries. Review and complete the private solo level playtests before publishing an opted-in edition. Because live rooms bind only published snapshots, run an owner-approved two-device acceptance after publication and before adopting it into lessons, including guest movement/firing, separate goals/points, pause/reconnect, private-room exclusion, public-seat admission and a third guest rejection. Do not create student identities or fabricate assessment results for acceptance.

CloudFormation structural/security checks in this repository complement formal validators. If `cfn-lint` or `cfn-guard` are unavailable, record that they did not run; service template/change-set validation and the independent runtime checks are separate evidence.

The managed relay uses AWS's documented [WebSocket lifecycle routes](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-websocket-api-overview.html) and scoped [connection callbacks](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-how-to-call-websocket-api-connections.html).
