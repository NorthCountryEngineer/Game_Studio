# Independent Game Studio service

## Ownership and deployment

Game Studio owns game definitions, private design conversations, playtest acknowledgements, publication snapshots, edition-specific high scores, agent/workflow configuration, its account invitations and branding. A host application owns its lessons, pages, course permissions, assessment policy and the association between a lesson and a Game Studio game ID. NCE Core owns identities, app membership, permissions and deployment authority.

The first implementation deliberately deploys one backend/frontend per Core tenant and environment. Tenant/service identifiers are server environment values, never selectors accepted from query parameters, messages or request bodies. Data keys and live introspection bind records to that installation. Different host applications in the same installation share its published catalog and edition boards; deploy separate installations when distinct content or score boundaries are needed.

AWS hosting uses Amplify for the static React frontend, API Gateway HTTP API and Lambda for the backend, on-demand DynamoDB tables for state, and private S3 for compatibility with the extracted assistant framework. Core resource credentials remain in the installation's SSM SecureString. No always-running Fargate service is needed for this workload. Model configuration stays separate from hosting and does not invoke a model.

The dedicated trusted Core deployment recipe is reviewed alongside this application. The generic `amplify-serverless` recipe is insufficient: it does not carry Game Studio's complete identity contract, assistant/game tables, runtime configuration and host framing policy. A marketplace identity registration alone does not provision hosting. Follow the Core onboarding guide before exposing this application in its deployment console.

## Authoring and publication

The host displays its creator link only to its own administrators. That link is a navigation convenience, not a permission grant. An allowlisted host can request automatic sign-in with `login=auto`; Game Studio consumes that navigation flag once after checking its own session and loading deployment configuration. Explicit host entry always reasserts Core's current browser account with Game Studio's own top-level PKCE authorization, discarding only its prior local target credentials and hiding the previous account's workspace. Cancellation cannot fall back to that previous account; ordinary non-auto visits retain session reuse. Game Studio checks current service-specific permissions after the callback and on every protected operation. An existing Core browser login and remembered Game Studio consent provide shared sign-in without reentering credentials; missing consent or an expired Core session can still need a Core page. An authenticated player without creator authority stays denied after reassertion. This avoids third-party cookie dependence and sending authorization codes or bearer tokens through an iframe.

`games-create` is delegated game creation administration. `games-publish` adds publication after playtesting. These are the named Game creation administrator and Game publishing administrator roles; they do not need the broader `games-manage` permission, which controls creation settings, branding and cross-content admin actions. `agents-manage` and `accounts-manage` independently control those workspaces. Ordinary authenticated players have no creation rights. Core organization administrators are not implicitly treated as Game Studio creators by the API.

Drafts stay private. Playtesting runs a validated data-only game specification inside a sandboxed frame with a fixed engine, nonce-bound messages and no network access. Generated content cannot add executable JavaScript, remote assets, new tools or mechanics beyond the supported engine. Agentic level planning remains constrained by the same schema. The free guided designer is deterministic; optional configured models can propose a tailored progression. All levels must be reviewed in the saved revision before a publisher can publish a copied snapshot.

`GameSpec` is a discriminated union: version 1/2 retain the existing arcade schema and version 3 carries one crossword, word search or Mad Libs definition. Word games have separate strict validators, deterministic bounded layout algorithms, and a fixed word-game sandbox. Browser and backend validators/layouts are checked against each other. The Lambda packager includes the new `word_games.py` module without changing table or identity configuration. A word game's single review item is `level-1`; editing clears its acknowledged revision, and publication still needs the separate human action. See [format definitions and limits](WORD_GAMES.md).

The optional existing model path is restricted to the current word-game format and administrator-defined usage limits. A model proposes data for that schema, never code or publication. All formats work through the free guided builder and direct editors without a model. Player letters, Mad Libs answers and completed stories are ephemeral inside the sandbox; outbound results contain only validated completion counts. Public puzzle definitions include their answers and are suitable for practice, not confidential tests. Completed puzzles can enter public fastest-time boards without an account. All published formats have a casual points, completion-time or survival board; see [public leaderboards](PUBLIC_LEADERBOARDS.md).

Publishing updates one canonical live edition. Hosts embed that canonical game ID, so a later publication becomes visible there; a stale score submission receives a reload error. Boards reset with each edition. Unpublishing removes public play and its board everywhere using that installation, while retaining the private draft. Deletion is explicit and requires the administrative capability.

## Live social deduction

Mafia is a separate live session category at `/mafia`; it does not extend or reinterpret the saved arcade/word-game specification union, publication records or assignment SDK. Names, avatars, private roles, choices, votes and text messages belong to temporary room sessions. The server assigns roles, validates authority and phase IDs, resolves rules and returns a separate projection for each capability-bound seat. A human narrator can see the room's private roles; automatic narration has no human omniscient seat. Anonymous players never gain creator or administrator permissions.

The existing game table holds at most 32 tracked room rows and one bounded installation index. Index and room creation, retirement and renewal are atomic. Active requests renew the room lease; abandoned rooms expire, and later room admission reclaims their rows. Public catalog scans filter out all room/index/narrator payloads and accept only structurally valid cursors across those rows. Capabilities are random, stored only as hashes on the server and never projected to another player. The client keeps its own seat locally and sends no Core token to room operations.

Optional AI narration reuses a reviewed installation-wide Nova Micro text vocabulary. Only protected administrator generation or separately authorized deployment initialization can invoke the model. Room creation, polling, actions and rematches are provider-free. Generated prose is inert, contains no player or secret-state inputs, and precedes canonical server facts. The game state machine alone controls progression and outcomes. See [Mafia](MAFIA.md) and [narration](MAFIA_NARRATION.md).

The public `/party` library adds five fixed online engines alongside Mafia, without changing any published GameSpec or assignment SDK. The independent `/party/rooms` adapter follows capability-bound, sequenced and conditional room transitions in bounded `game-party-room` and `game-party-index` records; existing Mafia records and routes remain independent. The canonical `config/party-games.json` is included in the Lambda package and frontend. All five engines are deterministic rules with bundled prompts/questions and no provider calls. See [party games](PARTY_GAMES.md).

Sketch & Guess renders local pointer ink independently of room requests. It streams quantized segments through that same serialized action sequence, retaining exact retries until acknowledgment. Canvas epochs fence clears, and phase IDs fence artist changes. The server validates artist authority and compacts old geometry within point, segment and byte limits; a separate bounded drawing parser handles dense projections without widening other game arrays. Mouse, pen and touch share pointer capture, with page gestures suppressed only on the canvas. See [drawing behavior and limits](PARTY_GAMES.md#drawing-on-desktop-and-mobile).

Optional AI opponents are server-owned seats in these existing private room engines. Only the human creator can add or fill AI seats in the lobby. They have no bearer credentials or membership records, cannot become host or human narrator, and are explicitly labeled in projections. Each policy receives only its own allowlisted player view and bounded private observation memory; normal game validators still enforce its choices. Authenticated human room requests apply at most eight due AI actions through the same conditional write, with no background workers, catch-up loops, model calls or autonomous lease renewal. Mafia's separate `automatic` narrator uses fixed server text; the existing reviewed AI narration vocabulary retains its administrative enablement boundary. Legacy rooms and saved game specifications remain compatible.

Each of the six games also has a local `/party/{kind}/host` controller for in-person play. It stores a bounded private session and a separate allowlisted public snapshot. A standalone `/party/present/{id}` entry mounts the public presentation without mounting App, Core sign-in effects or room requests. The projector consumes only the public storage key/broadcast channel named by a distinct view capability. It rejects private or unknown fields. Hidden roles, prompts, answers and choices enter that snapshot only at the host's explicit applicable reveal. The controller supports manual phase changes, score adjustments, outcomes, undo and local reset; browser-profile access is outside this presentation separation.

## Room passphrases

All six online party games and supported arcade multiplayer accept optional host-selected passphrases at room creation. Guests submit a phrase from the exact game's landing page, without a room URL or account. The shared data-only helper canonicalizes a bounded ASCII phrase and hashes it with a game-specific scope. Only the digest enters private room/index records; plaintext never enters public catalog/lobby projections, saved GameSpecs, provider input or browser storage. Existing invitation capabilities remain valid alternatives.

Party adapters reserve phrases within their existing bounded admission index. The arcade relay uses a bounded per-game registry in its existing table. Creation reserves the phrase conditionally with the room/publication checks; guest admission competes for the same phase/capacity-bound seat as an invitation. Closed and expired rooms release phrases without allowing an old request to enter a replacement room. Bounded hashed admission receipts preserve exact retries, with a shorter client retry window. Arcade phrase hosts additionally use a stable random request identity and capability to recover a lost creation reply. Requests renew ordinary active leases; passphrases do not create autonomous sessions.

Per-source and installation attempt limits constrain lookup traffic. Phrases confer only anonymous room admission, never host/narrator, creator or Core authority. No new infrastructure, IAM grant, schema migration, provider call or assignment SDK change is introduced. See [passphrase joining](ROOM_PASSPHRASES.md).

## Host embedding

`/embed/games/{id}` is the public player surface. Host IDs resolve only against operator-configured exact origins; the parent referrer must match. The hosting policy allows framing only by those origins. Private creation, account, settings and OAuth pages reject framing. The common SDK verifies sender origin, source window, channel, game ID, protocol version and message shape. Messages never carry identity, access tokens, roles or private drafts.

The exported completion event is a client-reported gameplay observation. It is suitable for UI feedback and an instructor's activity view; it is not proof of a student's identity, learning or grade. A host must bind activity to its own trusted session and instructor-approved assignment policy. Academy students need not become Core creators. Generated educational games remain private until an instructor/administrator reviews and publishes them.

The framework-independent SDK provides a separate version 1 assignment scoring policy and deterministic provisional calculators for all supported game formats. A host can reuse the same game on 25-point, 100-point or other bounded scales without editing the definition or casual board. Whole-game objective totals come from the validated snapshot; explicit arcade targets do not reuse the engine's conservative point ceiling. Optional publication hashing checks exact ID, edition and canonical definition bytes. Attempt selection uses host-issued ordinals, never browser time. Identity, enrollment, immutable policy review, attempt admission/idempotency, protected audit storage and final credit remain host responsibilities. Existing game specifications and version 1 completion messages are unchanged. See [assignment scoring](ASSIGNMENT_SCORING.md).

Public games and their arcade nicknames are publicly accessible. Approved embedding origins are a framing and integration boundary, not content confidentiality. Do not publish sensitive student information into game titles, descriptions, level text or nicknames. This release does not add private enrollment-based game distribution or automatically modify NCAcademy's lessons/accounts.

The unversioned public catalog remains compatible with legacy hosts by returning only version 1/2 games. Game Studio and its current SDK opt in to all formats with `specVersion=all`. Filtered pages retain their cursor even when empty. Direct published-ID lookup returns the saved versioned definition. NCAcademy's pinned data-import player remains a separate version 1/2 consumer; supporting version 3 there requires its own importer/player update and acceptance.

## Branding

An installation starts with its configured application name, badge, accent and optional public logo URL. A host keeps its own page chrome; the embedded service badge identifies the configured Game Studio installation. Hosts sharing that installation share its badge and catalog. Separate configured Core application installations can use different brands and data boundaries. An authorized Game Studio administrator can change branding in the UI using optimistic revision checks. Branding is plain text and an optional validated image URL. Host origins and return paths remain deployment settings because they must match API CORS and the CDN framing policy; a branding edit cannot change those security settings.

## Extraction and migration

The original Axolotl deployment and data are preserved. This repository contains the engine and authoring behavior, not a copy of live records. A host can adopt the standalone service incrementally through public links and the SDK. Moving existing drafts, accounts or score boards requires an explicit, reviewed data migration; changing endpoints alone is not such a migration.

## Optional multiplayer extension

Version 4 arcade editions opt in to two-player cooperative play while retaining saved levels and solo play. The parent page connects through an additive application-owned HTTP/WebSocket relay; the opaque game iframe remains network-disabled. A dedicated encrypted TTL table stores anonymous capability hashes and leases, never snapshots or student identities. The extension can read/condition-check the exact public-edition table and cannot access private drafts or Core credentials. The existing Core stack and shared permission boundary stay unchanged. Legacy catalogs still expose only versions 1–2; cooperative editions retain their exclusion from solo SDK completion and assignment scoring. Their individually observed final results can enter the public casual leaderboard. See [MULTIPLAYER.md](MULTIPLAYER.md) for lifecycle, testing and both release steps.

Rooms are private by default. Explicit public visibility adds a bounded installation-scoped waiting-room index to the existing relay table; listings contain only public game metadata and room IDs. Admission rechecks a live host, an unclaimed guest seat and the exact current publication in conditional transactions. Public and invitation joins compete for the same seat. Authenticated socket activity renews idle retention rather than imposing a fixed 30-minute room-age cap. Socket replacement preserves the mounted world; API Gateway's individual two-hour connection limit and host reconnect grace remain separate transport bounds. No new infrastructure, private-table access or identity grants are needed for the lobby.

Shooting Asteroids editions without a custom flow additionally support a room-level `versus` match. The host chooses bounded lives and duration when creating the room; the server stores those settings independently of the immutable publication and rechecks eligibility outside the publication-schema cache. Both seats and public listings receive the same settings. The fixed host simulation uses one arena, opponent projectile hits, respawn protection and explicit terminal winner/draw data. The relay validates snapshots against the room's settings; the guest sends only input. Missing match settings retain the existing cooperative opt-in and snapshot rules. Competitive matches do not emit solo/campaign completion or enter the existing solo leaderboard. No saved GameSpec format or authored level data changes. See [Asteroids versus](ASTEROIDS_VERSUS.md).

Version 5 adds strictly configured Asteroids prizes and can be solo or cooperative. Its per-ship effects and bounded shared pickups are fixed engine data; snapshots retain the existing size and authority boundaries. Solo prize games retain normal completion/scoring; cooperative ones remain excluded from those solo contracts. Existing saved formats are unchanged. See [ASTEROID_PRIZES.md](ASTEROID_PRIZES.md).

Version 6 adds explicit Asteroids survival, size-stage and enemy-ship data while retaining the full authored level plan, optional prizes and optional cooperation. Endless survival uses the first saved level as its starting state and ignores saved goal/timer fields; disabling it restores the retained campaign. A private playtest-review message is distinct from terminal gameplay results and never becomes a score or host completion event. The workshop acknowledges the reviewed starting level before publication, while finite campaigns continue to require all saved levels. Existing formats are unchanged until an explicit edit. See [ASTEROID_CHALLENGES.md](ASTEROID_CHALLENGES.md).

Version 6 optionally carries bounded custom sprite pixels in the game definition. Both validators accept only fixed dimensions and canonical base64 RGBA bytes. The sandbox builds in-memory canvases with no image URLs or additional networking permissions. Private/public snapshot separation and exact publication hashes include those assets. Models never receive the pixel arrays and cannot invent uploaded assets. See [Asteroids customization](ASTEROID_CUSTOMIZATION.md).

Version 7 adds fixed pixel platformers with runtime player-selected cosmetics and collectible points. Finite solo level editions can carry a bounded ordered flow of levels, client-owned material references and an initial home screen. The outer player orchestrates steps while gameplay stays inside the fixed opaque sandbox. The approved parent resolves material under its own permissions; exact origin/window/channel/game/edition/run/request/node checks bind one pending completion. A required material gate cannot complete in standalone play. Flow telemetry contains counts and separate active/wall/material timing, never identity or answers. Clients retain admission, assessment and leaderboard authority. Legacy catalogs omit custom flows and version 7. Continuous Asteroids uses a separate editor while preserving saved levels. See [level flows](LEVEL_FLOWS.md).

Version 8 composes bounded copies of complete solo game definitions and neutral client objects. It preserves each child's fixed sandbox and level flow, with version 4 host messages binding outer/inner object paths to the exact run and publication. A final continuous free-play copy begins after a single frozen completion; its points and time never modify the main result. Every outer step needs human review, including all child levels and the continuous review. Models cannot replace composition through conversation; authorized data-only authoring uses the same strict validators. No live game references, recursive journeys, new permissions or data migrations are introduced. See [multi-game journeys](MULTI_GAME.md).

## Crossword authoring assistant

A separate optional `crosswordAssistantModeId` selects a bounded Bedrock writing mode for author-time answer/clue proposals. The protected private operation uses the existing draft/configuration transactions, durable billable reservation and live Core/registry rechecks. The proposal is cached privately; the editor applies only a creator-selected, fully validated connected set. Version 3 snapshots, seeded layouts, public scoring and player load behavior remain unchanged. No model is called during play. See [crossword suggestions](CROSSWORD_GENERATION.md).
